# Workflow customizations

This project's additions to and changes of the workflow in `WORKFLOW.md`, which is generated by the `repo` skill and kept as generated. Read after it; where they conflict, this file applies, except that it can never relax a hard rule.

## Branching

- **`develop` is the work-in-progress trunk, and most work is committed to it directly.** Fixes, small features, documentation and dependency updates go straight onto `develop` — no branch, no pull request.
- **A separate feature branch only when asked.** Create one only when the user explicitly asks for it, or when the work is a large feature _and_ the user has explicitly confirmed they want it on its own branch — ask first rather than assuming. Such a branch is created from `develop`, and its pull request targets `develop`.
- **Never commit to `master`, or onto a detached HEAD.** If the current branch is `master` (or there is none), stop and ask where the work should go: normally `develop` or a new feature branch.
- **Propose a feature branch when a change warrants one**: say so and let the user decide; never branch on your own.
- **`master` holds only the latest stable release.** It is never committed to directly and never receives feature pull requests — it is only updated by merging `develop` into it when a stable version is released.
- Pull request titles follow `.github/pull_request_template.md`: `Issue #NN, Copied issue title`, with Changes / Testing / Impact sections.
